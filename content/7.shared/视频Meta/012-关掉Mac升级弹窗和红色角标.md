## 关掉 Mac 升级弹窗和红色角标

相关代码:本文即完整命令清单,无需另外下载



> [!info] 本节解决的两件事
> - **弹窗**:屏幕上飘出来的通知横幅,发送者是一个叫 `SoftwareUpdateNotificationManager` 的后台服务。
> - **红色角标**:系统设置(以及 Dock 上的齿轮图标)右上角那个红点,来源是「已检测到可用更新」这条缓存记录。
>
> 关掉服务 ≠ 红点消失,清掉红点 ≠ 弹窗不来。两段各做各的。

---

## 最简版

不想看原理的,照抄这几条就行。

**关弹窗**

```bash
# 禁用发弹窗的服务(输入管理员密码后 SIP 报错可忽略,禁用其实已经生效)
sudo launchctl disable gui/$(id -u)/com.apple.SoftwareUpdateNotificationManager

# 结束还在跑的那个进程
pkill -9 -f SoftwareUpdateNotificationManager
```

**关红标**

```bash
# 挡住更新检查的域名(没挂代理时靠这条)
sudo sh -c 'echo "0.0.0.0 swscan.apple.com" >> /etc/hosts'

# 不再自动检查更新
sudo defaults write /Library/Preferences/com.apple.SoftwareUpdate AutomaticCheckEnabled -bool false

# 清掉"有更新可用"的历史缓存
sudo sh -c 'defaults delete /Library/Preferences/com.apple.SoftwareUpdate RecommendedUpdates; killall softwareupdated 2>/dev/null; true'

# 清掉图标上当前那个红点
defaults write com.apple.systempreferences AttentionPrefBundleIDs 0
osascript -e 'quit app "System Settings"'; killall Dock
```

> [!warning] 挂了代理的话还要加一条
> 上面那条 hosts 会被代理绕过(原因见第四节)。在代理软件的规则里加一行,如Shadowrocket 放 `[Rule]` 段顶部:
> ```
> DOMAIN,swscan.apple.com,REJECT
> ```

**全部撤销**

```bash
# 恢复弹窗
sudo launchctl enable gui/$(id -u)/com.apple.SoftwareUpdateNotificationManager

# 恢复更新检查(记得同时删掉代理里那行规则)
sudo sed -i '' '/swscan.apple.com/d' /etc/hosts
sudo defaults write /Library/Preferences/com.apple.SoftwareUpdate AutomaticCheckEnabled -bool true
```

> [!note] 屏蔽期间的另一个影响
> 手动检查更新也会失败;走同一通道的 Xcode Command Line Tools 安装/更新、Rosetta 2 安装同样受影响。不影响 App Store 应用更新、iCloud、推送和日常浏览。

## 一、初始方案

Mac 时不时弹一次「升级到 macOS Tahoe」。不管它,它就一直挂在屏幕上挡着你正在看的东西,一天弹好几次,专注全被打断。

在系统设置里关闭自动更新,照着网上的方法照着跑了,第二天它照样弹。



---

## 二、找出发弹窗的那个服务

通过设置关闭自动更新等方法不能阻止弹窗,转换思路,去找发弹窗的那个服务
通过名字去后台服务里搜:

```bash
ls /System/Library/LaunchAgents/ | grep -i softwareupdate
```

会找到 `com.apple.SoftwareUpdateNotificationManager.plist`。打开它的配置核对一遍:

```bash
plutil -p /System/Library/LaunchAgents/com.apple.SoftwareUpdateNotificationManager.plist
```

输出里 `LaunchEvents` 那段说明了它什么时候会被叫醒(节选):

```
"UpdatesAvailable"    => "com.apple.SoftwareUpdate.updatesAvailable"
"BadgingCountChanged" => "com.apple.SoftwareUpdate.BadgingCountChanged"
```

对上了:**检测到有可用更新,就把它叫起来发通知**。发弹窗的人抓到了。

第二条 `BadgingCountChanged`(角标数变化)先记住——那是后面红点那条线的线索。

> [!tip] 可迁移的排查思路
> 这个路子不只对升级提醒有效:**去 `/System/Library/LaunchAgents/` 里按关键词反查服务 → 用 `plutil -p` 看它的唤醒事件**。任何一条「设置里关不掉」的系统通知,都可以照这个思路往下挖。

## 三、禁用它

```bash
sudo launchctl disable gui/$(id -u)/com.apple.SoftwareUpdateNotificationManager
```

输入管理员密码后,**大概率会看到这句报错**:

```
Boot-out failed: 150: Operation not permitted while System Integrity Protection is engaged
```

> [!note] 这个报错可以不管
> `disable` 那一步**已经写进去了**,报错的是紧跟着的「把正在跑的进程卸载掉」——系统自带服务不允许这样卸载。我们手动把残留进程结束掉即可,因为服务已经是禁用状态,结束之后不会再被拉起来。

```bash
pkill -9 -f SoftwareUpdateNotificationManager
```

验收:

```bash
launchctl print-disabled gui/$(id -u) | grep SoftwareUpdateNotification
```

输出那行末尾是 `disabled` 就成了,同时 `pgrep -f SoftwareUpdateNotificationManager` 应该查不到进程。

整个过程只写了一个禁用标记,落点在:

```
/var/db/com.apple.xpc.launchd/disabled.<你的uid>.plist
```

**没有动任何系统文件,也不需要关掉 SIP。**

### 代价与恢复

关掉的只是 **macOS 系统更新提醒**这一条线:

- 第三方软件自带的更新器照常提醒。查一下状态就能看到对比:

```bash
launchctl print-disabled gui/$(id -u) | grep -iE "update|appstore"
```

```
"com.microsoft.update.agent"  => enabled
"com.google.GoogleUpdater.wake" => enabled
"com.apple.SoftwareUpdateNotificationManager" => disabled
```

- 真正的代价只有一项:**系统安全更新也不弹提醒了**。检测本身还在跑,想看的时候手动敲一条:

```bash
softwareupdate -l
```

- 想恢复,把 `disable` 换成 `enable`,重启即可:

```bash
sudo launchctl enable gui/$(id -u)/com.apple.SoftwareUpdateNotificationManager
```

## 四、红点为什么清了又回来

弹窗没了,系统设置图标上那个红色 ① 还在。搜到的标准答案是这条:

```bash
defaults write com.apple.systempreferences AttentionPrefBundleIDs 0 && killall Dock
```

跑完**纹丝不动**。

原因不是命令写错了,而是它管的不是你这个场景:这条只负责「App **没在运行**时」Dock 显示的角标。而你排查的时候一直开着系统设置——**运行中的 App 会自己往图标上挂角标**,正好每次都盖在你刚清完之后。所以观感就是「清了没反应」。

红标一共三层,每清一层就被下一层顶回来:

| 层    | 是什么                                                                    | 顶回来的原因        |
| ---- | ---------------------------------------------------------------------- | ------------- |
| Dock | `AttentionPrefBundleIDs` 键                                             | App 在运行就被进程盖写 |
| 进程   | 运行中的系统设置自己挂标                                                           | 依据是下面那层缓存     |
| 缓存   | `/Library/Preferences/com.apple.SoftwareUpdate` 的 `RecommendedUpdates` | 每次成功检查更新就重新写入 |

所以要让它**开着设置也不挂标**,只有一个办法:让更新检查的实时查询失败。

### 最大的坑:hosts 被代理绕过

按常理写个 hosts 屏蔽掉苹果的更新检查域名:

```bash
sudo sh -c 'echo "0.0.0.0 swscan.apple.com" >> /etc/hosts'
```

**没拦住**。`softwareupdate -l` 照样查得到更新。

原因是全局流量走代理隧道,**代理自己解析域名(fake-IP),根本不看 `/etc/hosts`**。一条命令就能看出是谁在解析:

```bash
dscacheutil -q host -a name swscan.apple.com
```

```
name: swscan.apple.com
ipv6_address: ::ffff:198.18.0.41      ← 代理的 fake-IP 段,说明是代理在解析

name: swscan.apple.com
ip_address: 0.0.0.0                   ← 这才是 hosts 写进去的那条
```

`198.18.0.0/15` 是 fake-IP 常用段。**只要看到这个段,就说明这个域名的解析权在代理手里,改 hosts 是没用的。** 这个坑对所有挂全局代理的人通用,不限于本文这个场景。

### 三层一起上

1. **代理规则 REJECT**(核心,代理开着时生效)。以 Shadowrocket 为例,配置 `[Rule]` 段顶部加一行:

```
DOMAIN,swscan.apple.com,REJECT
```

2. **hosts 兜底**(代理关闭时生效),即上面那条 `echo >> /etc/hosts`。

3. **关自动检查 + 清掉历史缓存**。缺这步前两层都加了红标照样在,因为读的是旧缓存:

```bash
sudo defaults write /Library/Preferences/com.apple.SoftwareUpdate AutomaticCheckEnabled -bool false
sudo sh -c 'defaults delete /Library/Preferences/com.apple.SoftwareUpdate RecommendedUpdates; killall softwareupdated 2>/dev/null; true'
defaults write com.apple.systempreferences AttentionPrefBundleIDs 0
osascript -e 'quit app "System Settings"'; killall Dock
```

**验收**:重新打开系统设置,侧栏「有软件更新可用」整行消失,Dock 齿轮无红标。也可以直接查缓存是不是空的:

```bash
defaults read /Library/Preferences/com.apple.SoftwareUpdate | grep -A2 RecommendedUpdates
```

看到 `RecommendedUpdates = ( )` 就对了。

### 代价与恢复

- 屏蔽期间**手动检查更新也会失败**;走同一通道的 **Xcode Command Line Tools 安装/更新、Rosetta 2 安装**也会受影响。
- **不影响** App Store 应用更新、iCloud、推送、日常浏览。
- 想装更新时先删规则:删掉代理里那行,再执行

```bash
sudo sed -i '' '/swscan.apple.com/d' /etc/hosts
```

## 五、网上那条命令为什么没用

几乎所有教程都会给这一条:

```bash
sudo softwareupdate --ignore "macOS Tahoe"
```

它不是一直没用,而是**从 macOS 12.3 开始,只对受管理的设备(公司统一管理、带 MDM 描述文件的电脑)有效**。个人机器上跑完不会报错,也不会有任何变化——这是最容易误判「我是不是哪里做错了」的地方。

但它现在还挂在搜索结果里,一篇抄一篇。

**我们搜到的是别人机器上的答案,而且可能已经过期。**这两段排查真正值钱的不是命令本身,而是同一个套路:先确认刚才那步到底写进去没有,没生效就往下问「是谁在做这件事」。

# 补充

## 禁用状态可能被系统还原

写这篇时回头复查了一遍我自己的机器:第三节那个 `disable` 标记**已经不在** `disabled.<uid>.plist` 里了,`launchctl print` 显示这个 LaunchAgent 又是注册可用的状态。

用户域的禁用标记会被系统更新、部分迁移/修复操作重置。所以:

- 如果过一阵弹窗回来了,**先跑一次验收命令**(`launchctl print-disabled ... | grep SoftwareUpdateNotification`)看标记还在不在,而不是怀疑方法失效;
- 不在就把 `disable` 那条重跑一遍。

反过来,第四节那三层(代理规则 + hosts + 关自动检查)复查时都还在生效——`RecommendedUpdates` 是空的,红标也没回来。**想长期清净,第四节比第三节更耐久。**

## 环境说明

本文命令在 **macOS 15.2 (24C101)** 上实测。路径与键名在 macOS 13~15 上一致;更早的系统 `launchctl print-disabled` 输出格式可能略有差异,以实际输出为准。
