## Turning off the macOS upgrade nag and its red badge

Code for this episode: this page *is* the full command list — nothing to download.



> [!info] Two separate problems here
> - **The popup**: the notification banner that slides onto your screen. It's sent by a background service called `SoftwareUpdateNotificationManager`.
> - **The red badge**: the dot on the corner of System Settings (and the gear icon in the Dock). It comes from a cached "an update is available" record.
>
> Killing the popup won't clear the dot, and clearing the dot won't stop the popup. They're two separate jobs.


---

## The short version

If you don't care about the why, just run these.

**Stop the popup**

```bash
# Disable the service that sends the popup (you'll see an SIP error — ignore it for now and focus on the third command)
sudo launchctl disable gui/$(id -u)/com.apple.SoftwareUpdateNotificationManager

# Kill the process that's still running
pkill -9 -f SoftwareUpdateNotificationManager

# Don't skip this check: the output must end in "disabled". No output at all means the flag wasn't written — run it again
launchctl print-disabled gui/$(id -u) | grep SoftwareUpdateNotification
```

> [!important] Update, September 2026
> A while after running the commands above, the popup came back once. The fix is in the [[#Addendum|addendum]].


**Clear the red badge**

```bash
# Block the update-check domains (these two do the job when you're not on a proxy)
# swscan serves the regular update catalog, gdmf serves major-upgrade info — block only one and the new OS still gets found
sudo sh -c 'echo "0.0.0.0 swscan.apple.com" >> /etc/hosts'
sudo sh -c 'echo "0.0.0.0 gdmf.apple.com" >> /etc/hosts'

# Stop checking for updates automatically (this key doesn't stick — see the note below)
sudo defaults write /Library/Preferences/com.apple.SoftwareUpdate AutomaticCheckEnabled -bool false

# Wipe the cached "updates available" record
sudo sh -c 'defaults delete /Library/Preferences/com.apple.SoftwareUpdate RecommendedUpdates; killall softwareupdated 2>/dev/null; true'

# Clear the dot that's on the icon right now
defaults write com.apple.systempreferences AttentionPrefBundleIDs 0
osascript -e 'quit app "System Settings"'; killall Dock
```

> [!warning] Two more lines if you run a proxy
> Your proxy may bypass those hosts entries. Add the same two domains to your proxy app's rules — in Shadowrocket, put them at the top of the `[Rule]` section:
> ```
> DOMAIN,swscan.apple.com,REJECT
> DOMAIN,gdmf.apple.com,REJECT
> ```



**Bring the notification and the badge back**

```bash
# Bring the popup back
sudo launchctl enable gui/$(id -u)/com.apple.SoftwareUpdateNotificationManager

# Re-enable update checks (remember to delete the proxy rules too)
sudo sed -i '' -E '/(swscan|gdmf)\.apple\.com/d' /etc/hosts
sudo defaults write /Library/Preferences/com.apple.SoftwareUpdate AutomaticCheckEnabled -bool true
```

> [!note] One other thing you give up while this is in place
> Manual update checks will fail too, and so will anything that rides the same channel — installing or updating the Xcode Command Line Tools, and installing Rosetta 2. App Store app updates, iCloud, push notifications and normal browsing are unaffected.

## 1. The upgrade popup
### What I tried first

Every so often my Mac throws up an "Upgrade to macOS Tahoe" banner. Ignore it and it just sits there covering whatever you're reading, several times a day, breaking your focus every time.

I turned off automatic updates in System Settings and followed the fixes I found online. Next day it popped up again.

### Why the command everyone recommends does nothing

Nearly every tutorial hands you this one:

```bash
sudo softwareupdate --ignore "macOS Tahoe"
```

It's not that it never worked. **As of macOS 12.3 it only applies to managed devices** — machines under corporate management with an MDM profile. On a personal machine it runs without error and changes nothing, which is exactly why it's so easy to conclude you must have done something wrong.

And it's still sitting there in the search results, one post copying the next.

**What we find online is the answer for someone else's machine, and it may already be out of date.** This is where AI actually earns its keep: it can work from the live state of *your* machine instead.


---

### Finding the service that sends it

Since turning off automatic updates doesn't stop the banner, change tack: go find the service that actually sends it. Search the background services by name:

```bash
ls /System/Library/LaunchAgents/ | grep -i softwareupdate
```

That turns up `com.apple.SoftwareUpdateNotificationManager.plist`. Open its config and read it:

```bash
plutil -p /System/Library/LaunchAgents/com.apple.SoftwareUpdateNotificationManager.plist
```

The `LaunchEvents` section tells you exactly when it gets woken up (excerpt):

```
"UpdatesAvailable"    => "com.apple.SoftwareUpdate.updatesAvailable"
"BadgingCountChanged" => "com.apple.SoftwareUpdate.BadgingCountChanged"
```

There it is: **an available update is detected, the service gets woken, the notification goes out.** Culprit found.

Keep that second event — `BadgingCountChanged` — in mind. It's the thread that leads to the red dot later.

> [!tip] A troubleshooting habit worth stealing
> This approach isn't specific to update nags: **grep `/System/Library/LaunchAgents/` for a keyword, then read the service's wake-up events with `plutil -p`.** Any system notification you "can't turn off in Settings" can be traced the same way.

---

### Disabling the service behind the popup

```bash
sudo launchctl disable gui/$(id -u)/com.apple.SoftwareUpdateNotificationManager
```

Enter your admin password and **you'll almost certainly get this error**:

```
Boot-out failed: 150: Operation not permitted while System Integrity Protection is engaged
```

> [!warning] Don't just assume you can ignore that error
> The error is about the step right after the `disable` — unloading the process that's already running, which macOS won't let you do to a built-in service. That part really doesn't matter; just kill the leftover process by hand.
>
> But **don't take it as proof that the `disable` itself was written**. When I re-checked on 2026-09-10, this service was nowhere in the disabled list — while Google's and Microsoft's update agents sat right there in the same list marked `disabled`. The mechanism works fine; this one entry just never landed. So always run the check below, and if you don't see `disabled`, it didn't take — run it again.
>
> **And it goes further (2026-09-25): even when the flag is written, it isn't enough.** With `disabled` showing in the list, system events still wake the service and it still sends the popup. Details in the addendum at the end.

```bash
pkill -9 -f SoftwareUpdateNotificationManager
```

Verify:

```bash
launchctl print-disabled gui/$(id -u) | grep SoftwareUpdateNotification
```

If that line ends in `disabled`, the disable flag was written. On macOS 15.x, though, that **doesn't mean** the service won't run again — check `pgrep -f SoftwareUpdateNotificationManager` a while later and it'll most likely be back. The addendum explains why.

All of that wrote exactly one flag, here:

```
/var/db/com.apple.xpc.launchd/disabled.<your-uid>.plist
```

**No system files were touched, and you don't need to disable SIP.**

### What it costs, and how to undo it

The only thing you've switched off is **macOS system update notifications**:

- Third-party updaters keep notifying you as normal. You can see the contrast directly:

```bash
launchctl print-disabled gui/$(id -u) | grep -iE "update|appstore"
```

```
"com.microsoft.update.agent"  => enabled
"com.google.GoogleUpdater.wake" => enabled
"com.apple.SoftwareUpdateNotificationManager" => disabled
```

- The real cost is one thing: **you stop getting notified about security updates too.** The check itself still runs, so when you want to look:

```bash
softwareupdate -l
```

- To undo, swap `disable` for `enable` and reboot:

```bash
sudo launchctl enable gui/$(id -u)/com.apple.SoftwareUpdateNotificationManager
```

## 2. Why the red dot keeps coming back

The popup is gone, but the red ① is still sitting on the System Settings icon.
The usual answer you'll find is this:

```bash
defaults write com.apple.systempreferences AttentionPrefBundleIDs 0 && killall Dock
```

Run it and **absolutely nothing happens**.

The command isn't wrong — it just doesn't govern your situation. It only controls the Dock badge for an app that **isn't running**. And while you're troubleshooting, System Settings is open the whole time — **a running app badges its own icon**, overwriting yours right after you clear it. So it looks like the command does nothing.


The badge has three sources.
Clear only one of them and the others push it straight back; the dot only goes away once all three are cleared.

| Layer   | What it is                                                              | Why it comes back                          |
| ------- | ----------------------------------------------------------------------- | ------------------------------------------ |
| Dock    | the `AttentionPrefBundleIDs` key                                        | overwritten while the app runs             |
| Process | System Settings badging itself while open                               | it reads the cache below                   |
| Cache   | `RecommendedUpdates` in `/Library/Preferences/com.apple.SoftwareUpdate` | rewritten on every successful update check |


```bash
# Block the update-check domains (these two do the job when you're not on a proxy)
# swscan serves the regular update catalog, gdmf serves major-upgrade info — block only one and the new OS still gets found
sudo sh -c 'echo "0.0.0.0 swscan.apple.com" >> /etc/hosts'
sudo sh -c 'echo "0.0.0.0 gdmf.apple.com" >> /etc/hosts'

# Stop checking for updates automatically (this key doesn't stick — see the note below)
sudo defaults write /Library/Preferences/com.apple.SoftwareUpdate AutomaticCheckEnabled -bool false

# Wipe the cached "updates available" record
sudo sh -c 'defaults delete /Library/Preferences/com.apple.SoftwareUpdate RecommendedUpdates; killall softwareupdated 2>/dev/null; true'

# Clear the dot that's on the icon right now
defaults write com.apple.systempreferences AttentionPrefBundleIDs 0
osascript -e 'quit app "System Settings"'; killall Dock
```

There's a trap here: if you're on a proxy, none of the above takes effect — you run it and the dot is still there.

In Shadowrocket, for example, add these two lines at the top of the `[Rule]` section:

```
DOMAIN,swscan.apple.com,REJECT
DOMAIN,gdmf.apple.com,REJECT
```


**Verify**: reopen System Settings — the whole "A software update is available" row should be gone from the sidebar, and the Dock gear should have no badge. Or just check that the cache is empty:

```bash
defaults read /Library/Preferences/com.apple.SoftwareUpdate | grep -A2 RecommendedUpdates
```

`RecommendedUpdates = ( )` means you're good.

### What it costs, and how to undo it

- While this is in place, **manual update checks fail too**, as do **Xcode Command Line Tools installs/updates and Rosetta 2 installs**, which ride the same channel.
- **Not affected**: App Store app updates, iCloud, push notifications, everyday browsing.
- When you do want to install an update, drop the rules first — delete the lines in your proxy, then:

```bash
sudo sed -i '' -E '/(swscan|gdmf)\.apple\.com/d' /etc/hosts
```

> Updated 2026-09-25. The video demonstrates the commands from "The short version" above. After recording, an "Updates available / New software is ready to install" notification showed up once more. What follows is the extra work it takes to keep the upgrade popup gone.

### Two more steps for the short version

On top of "The short version", do two more things.

**Step 1**: run this in Terminal (no sudo):

```bash
for k in UserNotificationDate MajorOSUserNotificationDate RecommendedUserNotificationDate; do
  defaults write com.apple.SoftwareUpdate "$k" -date "2099-01-01 00:00:00 +0000"
done
```

**Step 2**: install a configuration profile.
1. Copy the XML from [Gate 2](#gate-2-flip-the-master-switch-with-a-profile) below, then run this in Terminal:
   ```bash
   cd ~/Desktop && pbpaste > mac-update-quiet.mobileconfig && plutil -lint mac-update-quiet.mobileconfig && open mac-update-quiet.mobileconfig
   ```
   If you see `OK`, the file is fine (don't save it from TextEdit — Gate 2 explains why).
2. Open **System Settings → General → Device Management**, double-click "关闭 macOS 升级弹窗与红标" (the profile's display name) → Install → enter your login password.

**Verify**: you're done when this shows `DisableSoftwareUpdateNotifications = 1`.

```bash
defaults read "/Library/Managed Preferences/com.apple.SoftwareUpdate"
```

To undo: remove the profile, then run the three `defaults delete` commands under "Verifying and undoing" at the end.

The rest of this section explains how it works.

### Why the popup comes back

Digging through the system log and the `SoftwareUpdateNotificationManager` binary itself turned up a few things:

1. **`launchctl disable` can't hold it back.** The disabled list says `disabled`, but it's an SIP-protected system service, and it gets woken up anyway:

   ```bash
   launchctl print gui/$(id -u)/com.apple.SoftwareUpdateNotificationManager | grep -E "state|runs|immediate reason"
   ```
   ```
   state = running
   runs = 38
   immediate reason = xpc event
   ```

2. **It pops up from a local cache — no network needed.** The hosts / proxy rules above really do block the update check (the log shows the proxy returning 404 and the scan failing). But when the service sees "last scan failed", it falls back to `/Library/Updates/ProductMetadata.plist` — which still holds the macOS Tahoe entry from a successful scan months ago. That directory carries SIP's `restricted` flag, so **not even root can delete it**.

3. **Whether it pops up comes down to two checks.** Straight from the log:

   ```
   Check if exceeded last user notification update post date (...) with interval (259200.000000): 1
   Should show available updates notification? ... disableSUNotifications: 0, nowExceedsLastNotificationDate: 1 ...
   ```

   - `nowExceedsLastNotificationDate`: has it been more than **3 days** (259,200 seconds) since the last popup? That's why it shows up every few days.
   - `disableSUNotifications`: a master switch, read only from configuration profiles (managed preferences).

4. **You can't turn off automatic checks from the command line.** `softwareupdated` wipes `AutomaticCheckEnabled` within a dozen or so seconds of you writing it, and `softwareupdate --schedule off` is refused for lack of a private entitlement.

So the approach changes: if the cache can't be deleted, leave it — **just make both checks fail**.

### Gate 1: push the "last popup" date out to 2099

Run as your normal user, **no sudo**:

```bash
for k in UserNotificationDate MajorOSUserNotificationDate RecommendedUserNotificationDate; do
  defaults write com.apple.SoftwareUpdate "$k" -date "2099-01-01 00:00:00 +0000"
done
```

From now on, "more than 3 days since the last popup" is never true. In the log, a suppressed popup looks like `nowExceedsLastNotificationDate: 0`.

### Gate 2: flip the master switch with a profile

Copy the block below, then save it as `mac-update-quiet.mobileconfig` with the Terminal command that follows:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
	<key>PayloadContent</key>
	<array>
		<dict>
			<key>PayloadType</key><string>com.apple.ManagedClient.preferences</string>
			<key>PayloadIdentifier</key><string>local.su-quiet.prefs</string>
			<key>PayloadUUID</key><string>6F1C2B7E-3A4D-4C51-9E0B-7D2A1F5C8E31</string>
			<key>PayloadVersion</key><integer>1</integer>
			<key>PayloadDisplayName</key><string>软件更新:静默</string>
			<key>PayloadContent</key>
			<dict>
				<key>com.apple.SoftwareUpdate</key>
				<dict>
					<key>Forced</key>
					<array>
						<dict>
							<key>mcx_preference_settings</key>
							<dict>
								<key>DisableSoftwareUpdateNotifications</key><true/>
								<key>DisableSoftwareUpdateBadging</key><true/>
								<key>AutomaticCheckEnabled</key><false/>
								<key>AutomaticDownload</key><false/>
							</dict>
						</dict>
					</array>
				</dict>
			</dict>
		</dict>
	</array>
	<key>PayloadDisplayName</key><string>关闭 macOS 升级弹窗与红标</string>
	<key>PayloadIdentifier</key><string>local.su-quiet</string>
	<key>PayloadUUID</key><string>B8E4D0A2-91C7-4F3E-A6B5-2C9D8E7F1A40</string>
	<key>PayloadType</key><string>Configuration</string>
	<key>PayloadScope</key><string>System</string>
	<key>PayloadVersion</key><integer>1</integer>
</dict>
</plist>
```

Once it's on your clipboard, run this in Terminal — it writes the file straight from the clipboard, checks the format, and opens it:

```bash
cd ~/Desktop && pbpaste > mac-update-quiet.mobileconfig && plutil -lint mac-update-quiet.mobileconfig && open mac-update-quiet.mobileconfig
```

Only carry on once `plutil -lint` prints `OK`.

> [!warning] Don't save it from TextEdit
> TextEdit saves rich text (RTF) by default, and renaming the extension doesn't change that. Double-click the result and a red **Error** entry appears in Device Management, with a dialog saying `Could not open profile … (NSCocoaErrorDomain:3840)` — the file can't be parsed.
> If that happens, select the Error entry in Device Management, click "−" to remove it, and regenerate the file with the `pbpaste` command above. If you really want to use TextEdit, choose **Format → Make Plain Text** (⇧⌘T) before saving.

Then go to **System Settings → General → Device Management**, double-click the profile and click Install (on macOS 15, profiles live here, not under Privacy & Security). The four keys control, in order: the popup master switch, the badge, automatic checks, and automatic downloads. This goes through the system's sanctioned managed-preferences channel, so `softwareupdated` can't wipe it.

Confirm it took:

```bash
defaults read "/Library/Managed Preferences/com.apple.SoftwareUpdate"
```

> [!note] Results (since 2026-09-25, updated 2026-10-12)
> - The badge switch works: the log went from `Setting badge count to 0 (disabled: 0)` to `(disabled: 1)`.
> - The log confirms how the date gate decides (`nowExceedsLastNotificationDate: 0` means no popup).
> - The master switch works too: all 6 decisions in the log from 10-07 to 10-12 show `disableSUNotifications: 1`, and each time `containsActiveUpdates: 1` (an update really was waiting to install). So the system does read the undocumented `DisableSoftwareUpdateNotifications` key.
> - The two gates back each other up: if the system ever resets the date, the profile still holds — and vice versa.

### Verifying and undoing

Check its last few decisions:

```bash
/usr/bin/log show --last 14d --style syslog --predicate 'process == "SoftwareUpdateNotificationManager"' \
  | grep -E "Should show available|Post Update Available|Setting badge count" | tail -5
```

To undo:

```bash
defaults delete com.apple.SoftwareUpdate UserNotificationDate
defaults delete com.apple.SoftwareUpdate MajorOSUserNotificationDate
defaults delete com.apple.SoftwareUpdate RecommendedUserNotificationDate
```

Then remove the profile under **System Settings → General → Device Management**, and take out the hosts entries and proxy rules as described in "Bring the notification and the badge back" above.
