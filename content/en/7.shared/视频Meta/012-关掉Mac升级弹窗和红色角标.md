> [!info] Two separate problems here
> - **The popup**: the notification banner that slides onto your screen. It's sent by a background service called `SoftwareUpdateNotificationManager`.
> - **The red badge**: the dot on the corner of System Settings (and the gear icon in the Dock). It comes from a cached "an update is available" record.
>
> Killing the service won't clear the dot, and clearing the dot won't stop the popup. They're two separate jobs.

---

## The short version

If you don't care about the why, just run these.

**Stop the popup**

```bash
# Disable the service that sends the notification
# (an SIP error partway through is fine — the disable already took effect)
sudo launchctl disable gui/$(id -u)/com.apple.SoftwareUpdateNotificationManager

# Kill the process that's still running
pkill -9 -f SoftwareUpdateNotificationManager
```

**Clear the red badge**

```bash
# Block the update-check domain (this is the one that works when you're not on a proxy)
sudo sh -c 'echo "0.0.0.0 swscan.apple.com" >> /etc/hosts'

# Stop checking for updates automatically
sudo defaults write /Library/Preferences/com.apple.SoftwareUpdate AutomaticCheckEnabled -bool false

# Wipe the cached "updates available" record
sudo sh -c 'defaults delete /Library/Preferences/com.apple.SoftwareUpdate RecommendedUpdates; killall softwareupdated 2>/dev/null; true'

# Clear the dot that's on the icon right now
defaults write com.apple.systempreferences AttentionPrefBundleIDs 0
osascript -e 'quit app "System Settings"'; killall Dock
```

> [!warning] One more line if you run a proxy
> That hosts entry gets bypassed by your proxy (see section four for why). Add a rule in your proxy app instead — in Shadowrocket, put this at the top of the `[Rule]` section:
> ```
> DOMAIN,swscan.apple.com,REJECT
> ```

**Undo everything**

```bash
# Bring the popup back
sudo launchctl enable gui/$(id -u)/com.apple.SoftwareUpdateNotificationManager

# Re-enable update checks (remember to delete the proxy rule too)
sudo sed -i '' '/swscan.apple.com/d' /etc/hosts
sudo defaults write /Library/Preferences/com.apple.SoftwareUpdate AutomaticCheckEnabled -bool true
```

> [!note] One other thing you give up while this is in place
> Manual update checks will fail too, and so will anything that rides the same channel — installing or updating the Xcode Command Line Tools, and installing Rosetta 2. App Store app updates, iCloud, push notifications and normal browsing are unaffected.

## 1. What I tried first

Every so often my Mac throws up an "Upgrade to macOS Tahoe" banner. Ignore it and it just sits there covering whatever you're reading, several times a day, breaking your focus every time.

I turned off automatic updates in System Settings — the fix every search result gives you. Next day it popped up again.

---

## 2. Finding the service that sends it

Since turning off automatic updates doesn't stop the banner, change tack: go find the process that actually sends it. Search the background services by name:

```bash
ls /System/Library/LaunchAgents/ | grep -i softwareupdate
```

That turns up `com.apple.SoftwareUpdateNotificationManager.plist`. Open its config and read it:

```bash
plutil -p /System/Library/LaunchAgents/com.apple.SoftwareUpdateNotificationManager.plist
```

The `LaunchEvents` section tells you exactly when it gets woken up (excerpt):

```
"UpdatesAvailable"    => "com.apple.SoftwareUpdate.updatesAvailable"
"BadgingCountChanged" => "com.apple.SoftwareUpdate.BadgingCountChanged"
```

There it is: **an available update is detected, the service gets woken, the notification goes out.** Culprit found.

Keep that second event — `BadgingCountChanged` — in mind. It's the thread that leads to the red dot later.

> [!tip] A troubleshooting habit worth stealing
> This approach isn't specific to update nags: **grep `/System/Library/LaunchAgents/` for a keyword, then read the service's wake-up events with `plutil -p`.** Any system notification you "can't turn off in Settings" can be traced the same way.

---

## 3. Disabling it

```bash
sudo launchctl disable gui/$(id -u)/com.apple.SoftwareUpdateNotificationManager
```

Enter your admin password and **you'll almost certainly get this error**:

```
Boot-out failed: 150: Operation not permitted while System Integrity Protection is engaged
```

> [!note] You can ignore that error
> The `disable` **was written**. What failed is the step right after it — unloading the process that's already running, which macOS won't let you do to a built-in service. Just kill the leftover process by hand; the service is already flagged disabled, so nothing will restart it.

```bash
pkill -9 -f SoftwareUpdateNotificationManager
```

Verify:

```bash
launchctl print-disabled gui/$(id -u) | grep SoftwareUpdateNotification
```

If that line ends in `disabled`, you're done — and `pgrep -f SoftwareUpdateNotificationManager` should come back empty.

All of that wrote exactly one flag, here:

```
/var/db/com.apple.xpc.launchd/disabled.<your-uid>.plist
```

**No system files were touched, and you don't need to disable SIP.**

### What it costs, and how to undo it

The only thing you've switched off is **macOS system update notifications**:

- Third-party updaters keep notifying you as normal. You can see the contrast directly:

```bash
launchctl print-disabled gui/$(id -u) | grep -iE "update|appstore"
```

```
"com.microsoft.update.agent"  => enabled
"com.google.GoogleUpdater.wake" => enabled
"com.apple.SoftwareUpdateNotificationManager" => disabled
```

- The real cost is one thing: **you stop getting notified about security updates too.** The check itself still runs, so when you want to look:

```bash
softwareupdate -l
```

- To undo, swap `disable` for `enable` and reboot:

```bash
sudo launchctl enable gui/$(id -u)/com.apple.SoftwareUpdateNotificationManager
```

## 4. Why the red dot keeps coming back

The popup is gone, but the red ① is still sitting on the System Settings icon. The standard answer you'll find is this:

```bash
defaults write com.apple.systempreferences AttentionPrefBundleIDs 0 && killall Dock
```

Run it and **absolutely nothing happens**.

The command isn't wrong — it just doesn't govern your situation. It only controls the Dock badge for an app that **isn't running**. And while you're troubleshooting, System Settings is open the whole time — **a running app badges its own icon**, overwriting yours right after you clear it. So it looks like the command does nothing.

There are three layers to the badge, and clearing one just lets the next one push it back:

| Layer   | What it is                                                             | Why it comes back              |
| ------- | ---------------------------------------------------------------------- | ------------------------------ |
| Dock    | the `AttentionPrefBundleIDs` key                                        | overwritten while the app runs |
| Process | System Settings badging itself while open                               | it reads the cache below       |
| Cache   | `RecommendedUpdates` in `/Library/Preferences/com.apple.SoftwareUpdate` | rewritten on every successful update check |

So there's only one way to keep the badge off **even with Settings open**: make the live update check fail.

### The big trap: your proxy bypasses hosts

The obvious move is a hosts entry blocking Apple's update-check domain:

```bash
sudo sh -c 'echo "0.0.0.0 swscan.apple.com" >> /etc/hosts'
```

**It doesn't block anything.** `softwareupdate -l` still finds updates.

The reason: your traffic goes through a proxy tunnel, and **the proxy resolves domains itself (fake-IP). It never looks at `/etc/hosts`.** One command shows you who's doing the resolving:

```bash
dscacheutil -q host -a name swscan.apple.com
```

```
name: swscan.apple.com
ipv6_address: ::ffff:198.18.0.41      ← the proxy's fake-IP range: the proxy is resolving this
name: swscan.apple.com
ip_address: 0.0.0.0                   ← this is the hosts entry
```

`198.18.0.0/15` is the usual fake-IP range. **If you see that range, resolution for that domain belongs to the proxy and editing hosts will do nothing.** This trap applies to anyone running a global proxy, not just this scenario.

### All three layers at once

1. **A REJECT rule in the proxy** (the important one — this is what works while the proxy is on). In Shadowrocket, add one line at the top of the `[Rule]` section:

```
DOMAIN,swscan.apple.com,REJECT
```

2. **hosts as a fallback** (this covers you when the proxy is off) — the `echo >> /etc/hosts` line from above.

3. **Turn off auto-check and wipe the cached record.** Skip this and the badge stays even with the first two in place, because it's reading the stale cache:

```bash
sudo defaults write /Library/Preferences/com.apple.SoftwareUpdate AutomaticCheckEnabled -bool false
sudo sh -c 'defaults delete /Library/Preferences/com.apple.SoftwareUpdate RecommendedUpdates; killall softwareupdated 2>/dev/null; true'
defaults write com.apple.systempreferences AttentionPrefBundleIDs 0
osascript -e 'quit app "System Settings"'; killall Dock
```

**Verify**: reopen System Settings — the whole "A software update is available" row should be gone from the sidebar, and the Dock gear should have no badge. Or just check that the cache is empty:

```bash
defaults read /Library/Preferences/com.apple.SoftwareUpdate | grep -A2 RecommendedUpdates
```

`RecommendedUpdates = ( )` means you're good.

### What it costs, and how to undo it

- While this is in place, **manual update checks fail too**, as do **Xcode Command Line Tools installs/updates and Rosetta 2 installs**, which ride the same channel.
- **Not affected**: App Store app updates, iCloud, push notifications, everyday browsing.
- When you do want to install an update, drop the rules first — delete the line in your proxy, then:

```bash
sudo sed -i '' '/swscan.apple.com/d' /etc/hosts
```

## 5. Why the command everyone recommends does nothing

Nearly every tutorial hands you this one:

```bash
sudo softwareupdate --ignore "macOS Tahoe"
```

It's not that it never worked. **As of macOS 12.3 it only applies to managed devices** — machines under corporate management with an MDM profile. On a personal machine it runs without error and changes nothing, which is exactly why it's so easy to conclude you must have done something wrong.

And it's still sitting there in the search results, one post copying the next.

**What we find online is the answer for someone else's machine, and it may already be out of date.** The valuable part of this whole exercise isn't the commands — it's the routine: first confirm whether the step you just ran actually got written, and if it didn't take effect, ask "so who *is* doing this?" and keep going.

# Addendum

## The disabled flag can get reset

While writing this up I went back and re-checked my own machine: the `disable` flag from section three **was gone** from `disabled.<uid>.plist`, and `launchctl print` showed the LaunchAgent registered and available again.

Disable flags in the user domain can be reset by system updates and by some migration or repair operations. So:

- If the popup comes back after a while, **run the verification command first** (`launchctl print-disabled ... | grep SoftwareUpdateNotification`) to see whether the flag is still there, rather than assuming the method stopped working;
- If it's gone, just run the `disable` line again.

The three layers from section four, by contrast, were all still holding on re-check — `RecommendedUpdates` was empty and the badge hadn't returned. **For long-term quiet, section four outlasts section three.**

## Environment

These commands were tested on **macOS 15.2 (24C101)**. The paths and key names are the same across macOS 13–15; on older systems the output format of `launchctl print-disabled` may differ slightly, so trust what you actually see.
